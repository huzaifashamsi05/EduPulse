# EduPulse

An AI-powered student success and early-intervention platform. EduPulse predicts a
student's likely academic outcome (Dropout / Enrolled / Graduate), explains why the
model reached that prediction, and presents both to an academic advisor through a
web dashboard — with the explicit understanding that predictions support human
review and must never automate punitive decisions.

Built as a solo capstone project, end-to-end: ML pipeline → FastAPI backend →
React frontend, with no hardcoded predictions anywhere in the UI.

---

## 1. Problem

Universities often have thousands of students but limited academic-advising
capacity. By the time a student's struggle becomes obvious, intervention can come
too late. EduPulse explores whether historical enrollment and academic performance
data can help surface risk earlier, so a human advisor can reach out sooner.

## 4. System Architecture

```
React (Vite) frontend
        │  HTTPS / JSON
        ▼
FastAPI backend  ──────────────►  Sample student roster (JSON)
        │
        ▼
Single serialized preprocessing + model pipeline (joblib)
        │
        ▼
SHAP explainer (auto-detects Tree vs. Linear explainer by model type)
```

The frontend never receives a hardcoded prediction — the Dashboard and Students
pages read from a precomputed sample roster (itself generated by running the real
model over real data), and the Student Detail and New Prediction pages call the
live `/predict` and `/explain` endpoints on every load/submit.

## 5. ML Methodology

### Data split
70% train / 15% validation / 15% test, **stratified** on the target class to
preserve the real class balance (~50% Graduate, ~32% Dropout, ~18% Enrolled) across
all three splits. The test set is never touched until final model selection.

### Preprocessing
One `ColumnTransformer` (numeric scaling + categorical one-hot encoding + binary
passthrough), bundled inside the same serialized `Pipeline` object as the trained
estimator. The backend loads this single artifact and never re-implements or
duplicates the preprocessing logic — eliminating train/serve skew.

### Models compared
Logistic Regression, Random Forest, and XGBoost, each evaluated with **5-fold
stratified cross-validation** on the training split.

### Model selection
The final model is selected by **macro-F1**, not raw accuracy. This dataset is
imbalanced, and a model that only predicts the majority class ("Graduate") well
would still score high accuracy while badly under-serving the minority "Enrolled"
class — arguably the group where early intervention matters most. Macro-F1 weights
all three classes equally, exposing that weakness where accuracy would hide it.

**A note on reproducibility:** Logistic Regression and XGBoost scored within
~0.0002 macro-F1 of each other during development — a statistical tie. Which one
"wins" can flip between machines due to floating-point differences across NumPy/
SciPy versions. This was observed directly during development (see commit history)
and is treated as an honest finding rather than a bug: when two models are this
close, the "best" model is not a fixed fact. The current selected model and its
exact metrics are always available live at `GET /model/info` and the Model
Insights page — this README intentionally does not hardcode a single "winning"
number, since it can differ by machine.

### Evaluation
Full evaluation — accuracy, per-class precision/recall/F1, macro-F1, confusion
matrix, ROC-AUC (one-vs-rest, macro) — is computed for the final model on the
held-out test set and saved to `ml/reports/model_comparison_report.json`. The
Model Insights page in the app renders this data live, not a screenshot.

A majority-class baseline (~50% accuracy, ~0.22 macro-F1) is included for
comparison — the trained model substantially improves on it.

### Final model
The model is refit on train+validation data after model selection (maximizing
data for the deployed artifact), then re-evaluated on the still-untouched test
set for the final reported numbers.

## 6. API

Base URL: `http://127.0.0.1:8000`

| Method | Endpoint | Purpose |
|---|---|---|
| GET | `/health` | Liveness check |
| GET | `/model/info` | Model name, version, class labels, test metrics |
| GET | `/model/insights` | Full model comparison, confusion matrix, feature importance |
| POST | `/predict` | Live prediction for one student (36-field JSON body) |
| POST | `/explain` | SHAP-based local feature contributions for one student |
| GET | `/students` | List/filter the sample student roster (`?risk_band=`, `?course=`, `?limit=`) |
| GET | `/students/{id}` | One student's stored record |
| GET | `/analytics/summary` | Dashboard aggregate stats |

Interactive API documentation (Swagger UI): `http://127.0.0.1:8000/docs`

### Example: POST /predict

Request body (all 36 fields required — see `backend/app/schemas/prediction.py`):
```json
{
  "marital_status": 1, "application_mode": 17, "course": 9254,
  "admission_grade": 122.6, "curricular_units_2nd_sem_approved": 4,
  "...": "... (see schema for full field list)"
}
```

Response:
```json
{
  "prediction": "Graduate",
  "risk_band": "Low",
  "probabilities": { "Dropout": 0.19, "Enrolled": 0.24, "Graduate": 0.57 },
  "model_version": "2026-08-29-v1"
}
```

## 7. Frontend

React 19 + Vite, React Router for navigation, Recharts for charts. Six pages:
Dashboard, Students, Student Detail, New Prediction, Model Insights, About &
Responsible Use. All data-fetching pages implement loading, error, and empty
states. No prediction value in the UI is hardcoded — Student Detail and New
Prediction call the live `/predict` and `/explain` endpoints on every load/submit.

## 8. Local Setup

Prerequisites: Python 3.10+, Node.js 18+.

```bash
# 1. Clone and enter the repo, then create a Python virtual environment
python -m venv .venv
.venv\Scripts\activate          # Windows; use source .venv/bin/activate on Mac/Linux
pip install -r requirements.txt

# 2. Train the model (only needed once, or to reproduce from scratch)
cd ml/src
python train.py

# 3. Generate the sample student roster for the Dashboard/Students pages
cd ../../backend
python scripts/generate_sample_students.py

# 4. Start the backend
uvicorn app.main:app --reload --port 8000

# 5. In a second terminal: start the frontend
cd frontend
npm install
npm run dev
```

Open `http://localhost:5173`. The backend must be running on port 8000 for the
frontend to work (CORS is configured for `localhost:5173` specifically).

## 9. Environment Variables

None required for local development — the frontend's API base URL is currently
set directly in `frontend/src/api/client.js` (`http://127.0.0.1:8000`). For a
production deployment, this should be moved to a `VITE_API_BASE_URL` environment
variable.

## 10. Tests

Manual integration test performed and confirmed: changing an input value (e.g.
`curricular_units_2nd_sem_approved`) in the New Prediction form and resubmitting
produces a materially different Dropout probability (verified: 19% → 93% when
approved units dropped to 0), confirming the full UI → API → model → UI path is
live, not a static mockup.

## 11. Limitations and Responsible Use

- Test accuracy is roughly 74–78% and macro-F1 is roughly 0.70 depending on which
  model wins cross-validation on a given machine — a useful decision-support
  signal, not a certainty.
- The "Enrolled" outcome is the hardest class to predict (fewest training examples,
  behaviorally overlaps with both other classes).
- The model was trained on one historical dataset from one country's higher
  education system; its accuracy is not guaranteed to generalize to other
  institutions, time periods, or populations.
- Global feature importance can be inflated for high-cardinality categorical
  features due to how one-hot encoded contributions are aggregated.
- **EduPulse is a decision-support prototype for human academic advisors.** It
  must not be used to automatically remove, penalize, reject, rank, or discipline
  students. Predictions and explanations describe patterns in historical data —
  they do not prove causation, and should never replace a human conversation with
  the student.
